Problématique

La question centrale

Jusqu'où peut-on automatiser l'évaluation d'un besoin IA sans confier la décision à une IA ?

Les quatre douleurs constatées

  • Hétérogénéité — chaque département décrit son besoin dans son propre vocabulaire, sans structure commune
  • Coût de cadrage — plusieurs semaines d'échanges avant même de savoir si le projet est faisable
  • Incertitude de faisabilité — disponibilité des données et pertinence de l'IA évaluées « au jugé »
  • Absence de traçabilité — deux demandes équivalentes peuvent recevoir deux réponses différentes

Les trois sous-questions

  • Q1  Comment structurer un besoin exprimé en langage naturel sans imposer un formulaire rigide au métier ?
  • Q2  Comment obtenir un score de faisabilité reproductible alors qu'un LLM ne l'est pas ?
  • Q3  Comment tenir cette qualité sans envoyer les données hors du SI de l'entreprise ?
Problématique · analyse

Pourquoi la solution naïve ne tient pas

Premier réflexe testé : envoyer le formulaire au LLM et lui demander directement un score de 0 à 100 avec sa décision.

Écueil 1

Non-reproductibilité. Le même besoin soumis deux fois ne donne pas le même score. Impossible de défendre une décision devant un métier.

Écueil 2

Justification hallucinée. Le modèle produit un raisonnement plausible après avoir choisi le chiffre. La justification n'explique pas le score.

Écueil 3

Règles métier non pilotables. Changer un seuil ou une pondération suppose de réécrire un prompt et de tout re-tester à l'aveugle.

Le principe de conception qui en découle

  • Le LLM fait ce qu'il fait bien : lire, comprendre, classer des faits dans des catégories fermées
  • Le code Python fait ce qu'il fait bien : calculer, appliquer des règles, décider
  • Aucun chiffre de score ne sort jamais d'un modèle de langage

Arbitrages techniques et alternatives écartées

BesoinRetenuAlternatives écartéesRaison de l'arbitrage
Orchestration LangGraph Chaîne LangChain linéaire, agent ReAct autonome Le cadrage est un graphe d'états à branches conditionnelles avec une pause utilisateur. Un agent autonome aurait rendu le parcours non reproductible.
Recherche de similarité PostgreSQL + pgvector ChromaDB (implémenté puis retiré), Pinecone ChromaDB persiste sur le disque local : incompatible avec un déploiement conteneurisé sans état. pgvector garde une seule base transactionnelle, index HNSW cosinus.
API FastAPI (async) Flask, Django REST Pipeline dominé par des attentes réseau LLM : l'async est structurant. Validation Pydantic native et streaming SSE pour l'analyse en direct.
Décision Python pur Scoring par le LLM, modèle ML supervisé Ni jeu d'entraînement étiqueté, ni tolérance à l'aléatoire. Un barème codé est explicable, testable et modifiable par un ingénieur métier.
Inférence souveraine vLLM + Qwen 14B AWQ Ollama seul, API cloud uniquement Ollama sérialise les requêtes : bloquant en multi-utilisateur. vLLM apporte le batching continu et le JSON contraint par grammaire.
Persistance du graphe Checkpointer Postgres État en mémoire, ré-exécution complète Une clarification peut durer des heures. Sans checkpoint, chaque réponse imposait de rejouer tout le pipeline, avec un coût LLM inutile.

Solution · 03

Architecture déployée — trois plans indépendants

Plan applicatif

Un conteneur Docker sur Cloud Run : FastAPI reçoit la soumission de manière asynchrone et confie l'exécution au graphe LangGraph, sous les 60 secondes imparties.

Solution · 05 · cœur du système

Le moteur de décision — 5 piliers pondérés sur 100

Le LLM classe, il ne note pas. Chaque pilier est ramené à une catégorie fermée, convertie en points par une table Python.

Viabilité IA

30 pts

HIGHLY_VIABLE 30 · MARGINAL 15 · NOT_AI 0 · IMPOSSIBLE 0

Disponibilité des données

25 pts

READY 25 · UNLABELED_OR_MESSY 10 · NONE 0

Clarté du problème

20 pts

CLEAR 20 · PARTIAL 10 · VAGUE 0 · CONTRADICTORY 0

Faisabilité d'intégration

15 pts

SIMPLE 15 · MODERATE 10 · COMPLEX 5

Gouvernance & sécurité

10 pts

SAFE 10 · MODERATE_RISK 5 · CRITICAL_RISK 0

Le contrat entre le modèle et le code

Le LLM renvoie, pour chaque pilier, un objet strict — jamais un chiffre :

"data_readiness": {
  "category": "UNLABELED_OR_MESSY",
  "reason": "Historique de 4 ans en Excel,
   sans étiquetage des défauts."
}
  • Température 0 et JSON contraint par grammaire côté vLLM
  • Une catégorie inconnue vaut 0 point — jamais une valeur inventée
  • Faits absents → erreur explicite, pas de score par défaut

Décision et bonus d'antériorité

GO ≥ 70 CLARIFY 20 – 69 NO-GO < 20

+5 points si un projet historique similaire existe (≥ 0,50) : l'antériorité valorise, elle ne pénalise jamais — un projet sans précédent n'est pas puni.

Solution · 06

Cinq garde-fous éliminatoires

Un veto ne retire pas des points : il plafonne le score. Aucune addition de bons critères ne peut compenser un critère rédhibitoire.

Garde-fouPlafondDéclencheurCe que cela évite en production
Périmètre département10Demande hors du domaine du département sélectionnéQu'une demande atterrisse dans le mauvais backlog et mobilise la mauvaise équipe
Viabilité IA18NOT_AI ou IMPOSSIBLEDe lancer un projet IA là où un script suffit — ou de promettre l'impossible (prédiction boursière)
Éthique & sécurité10CRITICAL_RISKUn usage illégal ou non conforme RGPD : surveillance des salariés, génération de phishing
Contradiction45CONTRADICTORYDe chiffrer un besoin qui s'auto-contredit : la demande repart en clarification
Absence de données45NONEDe valider un projet sans jeu de données : cause n°1 d'échec des POC IA

Cas réel — Convertisseur CSV vers XML

Données prêtes (25), besoin clair (20), intégration simple (15), gouvernance (5) = 65 points bruts, soit un CLARIFY. Le veto NOT_AI le ramène à 18 : NO-GO, avec le motif « transformation déterministe, un script pandas suffit ».

Traçabilité de la décision

Chaque veto écrit son motif en base, aux côtés des 5 sous-scores et de la catégorie retenue par le LLM. L'ingénieur qui rouvre le dossier six mois plus tard reconstitue exactement pourquoi la demande a été refusée.

Solution · 07

RAG — la mémoire des projets déjà menés

Ici le RAG ne rédige rien : il répond à une seule question — « avons-nous déjà fait ce projet ? »

Chaîne de recherche

  • Construction d'une requête structurée : nom du projet, problème, résultat attendu, processus actuel, texte des PDF joints
  • Vectorisation par le modèle d'embedding actif (local ou cloud)
  • Recherche cosinus pgvector, index HNSW, top_k = 5
  • Filtrage préalable sur le département avant le calcul de similarité

Deux seuils, deux comportements

≥ 0,75  antériorité exacteFAST-TRACK

Le graphe court-circuite l'analyse LLM : score 95, réponse en moins de 3 secondes, coût d'inférence nul.

≥ 0,50  projet voisinBONUS +5

Les projets voisins sont cités dans le rapport comme références réutilisables.

Pourquoi pgvector plutôt qu'une base vectorielle dédiée

  • Sans état — aucun volume disque local à monter, compatible conteneur éphémère
  • Transactionnel — le vecteur et les métadonnées métier vivent dans la même transaction, donc jamais désynchronisés
  • Une seule base à exploiter — sauvegarde, migration et supervision mutualisées
  • Dimension configurable — 1024 avec qwen3-embedding, 768 avec nomic-embed-text, vérifiée au démarrage

Le déplacement technique de la Phase 4

La première implémentation utilisait ChromaDB en mode persistant sur disque. Fonctionnelle en local, elle devenait un point de blocage dès qu'on visait un déploiement conteneurisé sans état. La réécriture vers pgvector asynchrone a supprimé cette dépendance au système de fichiers.

Solution · 08

Clarification multi-tours avec reprise d'état

Quand le score tombe dans la zone grise, le système ne refuse pas : il pose les bonnes questions et reprend là où il s'était arrêté.

Bug rencontré

Un nœud unique générait les questions et portait la pause. Or la reprise ré-exécute le nœud depuis son début : à chaque réponse, un nouveau jeu de questions était produit. La boucle ne convergeait jamais.

Correction

Séparation en deux nœuds : generate_questions (effet de bord, exécuté une seule fois) et await_clarification_answers (pause pure, sans effet de bord). La reprise ne rejoue plus que le second.

Bénéfice mesuré

  • Avant : chaque réponse rejouait tout le pipeline depuis le début, RAG et extraction compris
  • Après : reprise au point d'arrêt, un seul appel LLM par tour
  • Garde-fou : 2 tours maximum, puis rapport partiel — pas d'interrogatoire sans fin
Solution · 09

Livrable final et supervision humaine

Cahier des charges généré

  • Rédigé en Markdown, diffusé token par token en SSE : l'utilisateur voit le rapport s'écrire
  • Contenu : contexte métier, faits extraits pilier par pilier, score détaillé, vetos et leurs motifs, projets historiques comparables, prochaines étapes recommandées
  • Version statique de secours construite en Python si le LLM est indisponible : l'utilisateur repart toujours avec un document
  • Persisté en base et exportable

Ce que le rapport change pour l'équipe

Le premier livrable d'un projet — le document de cadrage — existe avant la première réunion, au lieu d'en être le résultat.

Dashboard ingénieur IA

  • File des soumissions avec décision, score et statut
  • Override manuel : approuver un NO-GO, refuser un GO, forcer une clarification
  • Chaque override enregistre la décision précédente, la nouvelle, l'auteur et le motif
  • Le drapeau manual_override distingue toujours une décision humaine d'une décision calculée

Pourquoi l'humain garde la main

  • Le barème ne connaît ni l'agenda stratégique, ni le budget, ni la politique interne
  • Un refus automatique non contestable ferait rejeter l'outil par les métiers
  • L'historique des overrides est la matière première du futur ré-étalonnage du barème
Solution · 10

Souveraineté — aucune donnée métier vers une API tierce

Réponse à la sous-question Q3 : le moteur d'inférence est un branchement, pas une dépendance du code.

gemini_cloud

Mode développement et référence de qualité. Gemini Flash, rotation de clés, repli OpenAI.

openai_cloud

Fournisseur de repli sur erreur transitoire du fournisseur principal.

ollama_local

Poste de développement ou serveur interne. Protocole natif /api/chat.

lightning_vllm

Cible souveraine : vLLM sur GPU privé, protocole compatible OpenAI /v1.

Ce que l'abstraction a coûté — et rapporté

  • Ollama et vLLM parlent des protocoles incompatibles : un simple booléen « local / cloud » ne suffisait pas
  • Refonte en fournisseurs typés derrière une interface commune, sélectionnés par LLM_BACKEND
  • Repli en cascade, nouvelles tentatives avec backoff exponentiel, erreurs distinguées : transitoires ou définitives
  • Configuration validée au démarrage : un backend mal configuré échoue immédiatement, pas à la première soumission utilisateur

Déploiement GPU réalisé

  • Studio GPU Lightning AI (T4 / A10G), stockage de modèles persistant entre les sessions
  • Reverse proxy d'authentification Bearer avec support du streaming devant le moteur d'inférence
  • Qwen2.5-14B-Instruct-AWQ quantifié servi par vLLM — batching continu, 11 utilisateurs simultanés tenus
  • JSON contraint par grammaire (xgrammar) : l'extraction factuelle ne peut structurellement pas produire un JSON invalide
  • Embeddings servis localement, repli cloud uniquement si le mode le permet
Démonstration

Parcours utilisateur de bout en bout

Deux cas contrastés : une demande solide validée en quelques secondes, et une demande bloquée par un garde-fou éthique.

1 Dépôt

Choix du département, formulaire adapté, pièces jointes PDF analysées automatiquement.

2 Analyse en direct

Le flux SSE affiche chaque étape : recherche d'antériorité, extraction des faits, calcul du score.

3 Verdict

Score détaillé par pilier, catégories retenues, motifs des vetos éventuels.

4 Livrable

Cahier des charges rédigé en direct, ou questions de clarification si zone grise.

Cas A — GO OCR de factures fournisseurs

  • Antériorité détectée : 0,72 de similarité avec un projet passé → bonus appliqué
  • Piliers : viabilité 30, données 25, clarté 20, intégration 5, gouvernance 5
  • Score 85 / 100 → GO, cahier des charges généré
  • Durée totale du pipeline : 2,7 s

Cas B — NO-GO Générateur d'e-mails de phishing

  • Techniquement faisable — et c'est précisément le piège
  • Gouvernance classée CRITICAL_RISK → veto éthique, plafond à 10
  • Score 10 / 100 → NO-GO avec motif explicite
  • Le refus est justifié et tracé, il ne repose pas sur le refus d'un modèle

Ce que le barème garantit

Quel que soit le modèle, à faits identiques le score est identique — l'écart entre modèles porte sur la lecture du besoin, jamais sur le calcul. Le déterminisme est vérifié par les tests unitaires du moteur.

Scores instables Le LLM produisait directement le chiffre : deux exécutions identiques donnaient deux scores différents Séparation stricte extraction / décision. Le modèle ne renvoie que des catégories fermées ; le calcul passe en Python testé unitairement.
Boucle de clarification sans fin La reprise d'un graphe interrompu ré-exécute le nœud entier : les questions étaient régénérées à chaque tour Découpage en un nœud producteur et un nœud de pause sans effet de bord, avec état persisté dans un checkpointer Postgres.
Chaîne de migrations rompue Deux révisions initiales concurrentes et des colonnes absentes en base : divergence silencieuse entre modèles et schéma Réparation de la chaîne, puis test d'intégration en CI qui applique, annule et réapplique toutes les migrations sur un PostgreSQL réel.
Protocoles LLM incompatibles Ollama expose /api/chat, vLLM expose /v1 : un booléen « local / cloud » ne pouvait pas exprimer les deux Refonte en fournisseurs typés derrière une interface commune, sélection explicite du backend, repli en cascade et validation au démarrage.
Base vectorielle avec état ChromaDB écrit sur le disque local : incompatible avec un conteneur éphémère Réécriture vers pgvector asynchrone, index HNSW cosinus, vecteurs et métadonnées dans la même transaction.
Latence en multi-utilisateur Ollama traite les requêtes en série : le second utilisateur attend la fin du premier Passage à vLLM avec modèle quantifié AWQ, batching continu et JSON contraint par grammaire — 11 utilisateurs simultanés tenus.

  • Concevoir pour l'auditabilité autant que pour la fonctionnalité

Compétences transverses

Bilan · 03

Limites assumées et suites possibles

Limites actuelles

  • Barème calibré à la main : pondérations issues d'entretiens avec l'équipe, pas d'un historique statistique de décisions
  • Base d'antériorités réduite : le RAG ne devient réellement discriminant qu'avec un corpus de projets fourni
  • Jeu d'évaluation de 20 cas : suffisant pour la non-régression, insuffisant pour une mesure statistique fine
  • Pas encore en production : les gains sont estimés, pas observés sur des utilisateurs réels
  • Sécurité applicative minimale : ni SSO, ni RBAC fin — hors périmètre du stage

Perspectives, par ordre de valeur

  • Boucle d'apprentissage sur les overrides — comparer décisions calculées et décisions humaines pour ré-étalonner les pondérations sur des données réelles
  • Ingestion massive de l'historique projets — le fast-track ne prend sa valeur qu'à cette condition
  • Observabilité LLM — traces par exécution : coût, latence, dérive de qualité entre modèles
  • SSO d'entreprise et RBAC — condition d'ouverture à tous les départements
  • Élargissement du jeu d'évaluation à 100+ cas, avec régression automatisée à chaque changement de modèle
Conclusion

Retour à la question de départ

Q1 Structurer le flou

Un formulaire par département plus l'analyse des documents joints, transformés par le LLM en faits catégorisés sur cinq piliers — sans imposer de vocabulaire technique au métier.

Q2 Rendre la décision fiable

Le modèle classe, le code décide. Un barème pondéré et cinq garde-fous éliminatoires produisent un score reproductible et justifié, que l'ingénieur peut contester et surcharger.

Q3 Garder les données

Le moteur d'inférence est un branchement configurable : le même pipeline tourne sur un modèle open-weight servi par vLLM sur GPU privé, sans appel externe.

La valeur du système ne vient pas du modèle de langage, mais de la frontière qu'on trace autour de lui : lui confier la lecture du besoin, et jamais la décision.

Faisabilité d'intégration15SIMPLE 15  |  MODERATE 10  |  COMPLEX 5

Modificateurs

  • +5 si similarité RAG ≥ 0,50 (plafonné à 100)
  • Score forcé à 95 si similarité ≥ 0,75 → FAST_TRACK
  • Vetos : plafonds 10, 18 ou 45 selon le garde-fou déclenché

Seuils de routage

  • GO score ≥ 70 → rapport
  • NEEDS_CLARIFICATION 20 – 69 → questions
  • NO_GO score < 20 → rapport de refus motivé
  • Maximum 2 tours de clarification, puis rapport partiel

Garanties du moteur

  • Zéro appel LLM dans la fonction de scoring
  • Catégorie inconnue → 0 point, jamais de valeur par défaut inventée
  • Faits absents → exception explicite, pas de score silencieux
  • Fonction pure, couverte par des tests unitaires
Annexe A2

Modèle de données — 8 tables

submissions

Demande déposée : département, formulaire, texte des PDF analysés, statut courant.

departments

Configuration par département : champs du formulaire, périmètre attendu.

fact_extractions

Faits extraits par le LLM : catégorie et motif pour chacun des 5 piliers, modèle utilisé.

scoring_results

Score final, sous-scores, décision, vetos déclenchés et leurs motifs.

clarification_rounds

Questions posées et réponses reçues, tour par tour.

reports

Cahier des charges généré en Markdown, versionné par soumission.

reviewer_overrides

Décision humaine : ancienne valeur, nouvelle valeur, auteur, motif, horodatage.

historic_projects

Projets passés vectorisés — colonne vector pgvector, index HNSW cosinus.

Choix de persistance

  • Schéma détenu par Alembic — create_all réservé aux fixtures SQLite des tests unitaires
  • Faits, score et rapport écrits dans une transaction unique : jamais de score orphelin
  • Le contexte documentaire est conservé entre les tours de clarification
  • Checkpoints LangGraph stockés dans la même base, via un pool géré par le cycle de vie de l'application

Ce que la traçabilité permet

  • Rejouer une décision passée à l'identique et l'expliquer ligne par ligne
  • Mesurer l'écart entre décision calculée et décision humaine
  • Auditer quel modèle a produit quelle extraction (colonne de suivi du modèle)
  • Comparer deux modèles sur la même demande, à barème constant

Annexe A4

Stack technique et exploitation

Backend

  • Python 3.12, gestion des dépendances par uv
  • FastAPI asynchrone, validation Pydantic
  • LangGraph — graphe d'états, interruptions, checkpointer Postgres
  • SQLAlchemy async sur asyncpg, migrations Alembic
  • Streaming SSE pour l'analyse et la rédaction du rapport

Données & modèles

  • PostgreSQL 16 + pgvector, index HNSW cosinus
  • Embeddings : qwen3-embedding:0.6b (1024 d) ou nomic-embed-text (768 d)
  • LLM cloud : Gemini Flash, repli OpenAI
  • LLM souverain : Qwen2.5-14B-Instruct-AWQ servi par vLLM, ou Ollama
  • JSON contraint par grammaire (xgrammar) côté vLLM

Front & exploitation

  • React + Vite, 7 composants métier
  • Docker Compose : base, migration bloquante, backend, frontend, Adminer
  • GitHub Actions : tests, chaîne de migrations, construction d'image
  • Configuration par variables d'environnement, validée au démarrage
  • Journalisation structurée JSON en production
